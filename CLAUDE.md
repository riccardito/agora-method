# CLAUDE.md -- operating brief for an Agora repository

This file is loaded into every Claude Code session in this repository. It carries
the minimum an agent needs to work the Agora way; the reasoning lives in
[`docs/method.md`](docs/method.md) and in the files under [`.claude/`](.claude/).

## What this repository is

`agora-method` is the method layer of an AI-assisted development pipeline,
extracted from the project it was built for and published as a template. It holds
no product code. A child project copies `.claude/`, `agora/` and `agora_checks/`,
writes its own `CLAUDE.md` sections for its product, and starts a session.

## How work runs here

- **Four layers.** Orchestrators (`/agora` brackets a work session, `/plaza` runs a
  self-improvement round) -> skills (`.claude/skills/`, levelled draft -> used ->
  hardened -> reference) -> policies (`.claude/policies/`, mirrored below) -> tools
  and state (`agora_checks`, `.claude/sessions/`).
- **Work is bracketed by a session.** `/agora --start` reads the state, proposes a
  plan and the repo plan, and waits for a nod; `/agora --end` produces one close-out
  paper at one gate. Never open a second session on top of an open one.
- **The organising constraint:** a mechanism the orchestrator calls survives; a
  mechanism a human must remember does not. Prefer a check over a rule.
- **The checks:** `make check` runs all seven (`python -m agora_checks all`). Each
  prints `[FAIL]` lines and a summary; the exit code is the verdict.

## The planning vocabulary

The tier table is generated from [`agora/vocabulary.yaml`](agora/vocabulary.yaml)
into the orchestrator skill and `docs/method.md`; see the `## Goal vocabulary` section of
[`.claude/skills/agora/SKILL.md`](.claude/skills/agora/SKILL.md).

### policy-four-eyes -- Four-eye principle — propose, nod, then act at transition gates <sup>([full text](.claude/policies/policy-four-eyes.md))</sup>

<!-- rc:policy-four-eyes -->
1. **Apply at transition gates, not steps — and CONSOLIDATE gates that fire together.** session open (plan + repo plan, one gate) · **phase completion (mid-session)** · **session close (the close-out paper — ONE gate carrying commits, XP, dispatch, retro and Issue actions)** · Milestone firing (its own gate — a tag is irreversible) · mode switches. Never at every file edit, every tool call, every mid-loop sub-step. **Gate COUNT is itself the cost.** The US-AGORA-033 probe found `--end` expensive not for its eleven steps but for the four-to-five gates it serialized, while `--start` runs comparable machinery through one gate and is not experienced as expensive. When several proposals arrive at the same boundary, present them as **one paper with one nod**, not as a queue — but keep the summarized discipline of Rule 3, or consolidation becomes evasion. **For non-Agora skills: recognize, don't add.** `/implement-story` Phase 2b plan, `/feature-plan` decomposition, `/iterate` retro proposal — these are *already* 4-eye gates today. The policy names them; it does not multiply them. A skill that has a working natural gate adopts the policy implicitly by recognizing it; a skill with no obvious transition gate does NOT get one added just because the policy exists.
2. **Propose a default, never just list options.** A 4-eye gate is *"here's what I'd do — nod or redirect"*, never *"what do you want?"* without a recommendation. The agent names a recommended path; the user accepts, redirects, or asks for alternatives. Deferring decisions to the user is a *failure mode*, not the point of the gate. **Mechanism: prose is the default; a picker dialog (`AskUserQuestion`) is reserved for clean either/or separation.** A planning/discussion gate is a conversation — state the recommendation + reasoning in prose and invite a nod-or-redirect, so the user can read the reasoning and add free-form feedback. A dialog box *hides* the prose reasoning behind the picker and reduces the user to selecting a preset option — use it only for genuinely mutually-exclusive choices (Shape A/B/C, fix-now vs defer, promote/park/cancel), never for open discussion (`/agora` retro 2026-06-08).
3. **Summarized, not detailed.** The proposal fits in one glance — grouped files + one-line subjects (commit-tree triage), plan phases + one-line gates (session open), N criteria max (Milestone firing). Full bodies after the nod, never before. Detailed proposals turn "nod" into reflexive rubber-stamping; the user can't pattern-spot in a wall of text.
4. **Smoke-test pass ≠ user nod.** Tooling green (ruff, tests, lint, type-check, smoke verification) is a *prerequisite* to asking, never a substitute for asking. The 4-eye gate fires only on explicit textual "yes" / "nod" / "go" / equivalent — never inferred from "tests passed".
5. **The gate is bidirectional — for tweaks, not just safety.** The user's nod often includes *"while we're there, also do X"* or *"wait, what about Y?"*. The gate is half error-prevention, half small-improvement discovery. The agent treats redirects as expected, not as cost.
<!-- /rc:policy-four-eyes -->

### policy-shoulder-glance -- Shoulder-glance — the Schulterblick reflex (glance back before moving on) <sup>([full text](.claude/policies/policy-shoulder-glance.md))</sup>

<!-- rc:policy-shoulder-glance -->
1. **The shoulder-glance fires before leaving any chapter** — a phase, a session, a topic, or an Era. It is a **retrospective over the whole span just finished** (the time "at the seat"), not a final-moment loss-check. Three checks: **(1) have I missed something? · (2) what have I used? · (3) how should it look?**
2. **Both halves — catch AND close.** The glance surfaces anything left behind (the *safety* half) **and** summarizes what was engaged + used to **close the chapter** (the *closure* half). The closure is what licenses moving forward with confidence. A glance that only does the safety half is incomplete.
3. **Sibling of `policy-four-eyes` — backward-looking, not forward.** Four-eyes is *propose-and-confirm at a transition gate* (forward-looking: "here's what I'd do — nod?"). Shoulder-glance is *retrospective summary-and-leftover-check before leaving* (backward-looking: "here's what just happened — anything dropped?"). The two pair at a boundary: glance back, then propose forward.
4. **It is the fractal skeleton's slots 4 + 5.** The glance is the concrete act of **slot 4 (evaluation / open-thread handling)** and **slot 5 (ending: summarize + close)** of the planning skeleton (`agora-planning-skeleton.md`). It gives the skeleton's "ending" a defined ritual.
5. **Recognize, don't multiply.** The glance *names* a reflex Agora already does through scattered mechanisms — open-threads capture (`THREADS.md`), Issue documentation, the implementation-plan Surprises-&-decisions log. It unifies them as one discipline and wires into the **existing** fires (`/agora --end`, `/plaza` close-out, the Era off-boarding "finish old Era" movement). It adds **no new gates** beyond those (per `policy-four-eyes` Rule 1, "recognize, don't add").

### policy-skill-authoring -- Skill authoring — the static shape of a SKILL.md <sup>([full text](.claude/policies/policy-skill-authoring.md))</sup>

<!-- rc:policy-skill-authoring -->
1. **This policy owns the static shape of skill AND policy files; `policy-skill-progression` owns the level transitions.** Every requirement on what a `SKILL.md` / `experience.md` / `policy-*.md` *contains* (frontmatter fields, body sections, quoting, categorization) lives here; how a skill *moves* between levels (metrics, gates, promotion, regression, ceremony) lives there. The enforcement arm is `scripts/checks/validate_skill_frontmatter.py` (`--levels`, default ON) — wired into `/agora --start` step 1.1, the pre-commit hook, and CI.
2. **Frontmatter prose scalars MUST be double-quoted** when the value contains `: ` (colon-space), whitespace-`#`, a leading `[`/`{`, a mid-string `|`/`>`, a `<`/`>` anywhere, or a leading reserved indicator (`& * ! ' " % @` backtick). Unquoted, they crash the VS Code extension's strict YAML parser with `Unhandled case: [object Object]` and block the user from seeing assistant responses — even though the harness's tolerant parser accepts them.
3. **Frontmatter fields gate by level** (lint-checked): `level:` ∈ `draft / used / hardened / reference` (missing → `draft`); `role:` required at `used`+; `epithet:` required at `hardened`+; a parsing `experience.md` sidecar (with `xp_total`) required at `used`+. Only `/level` writes `level:` / `promoted_at:` / `role:` / `epithet:` — direct edits violate `policy-skill-progression` Rule 5.
4. **Body sections gate by level** (lint-checked): every `SKILL.md` body has ≥1 `## ` heading; `hardened`+ adds a `## When NOT to use` (or equivalent boundary) section and a `## Claims at this level` section with ≥3 named invariants; `reference` adds a `## Identity` opening section. These are the deterministic, file-checkable artifacts the promotion quests require.
5. **A scattered rule earns its own policy when it lives in ≥3 places** (the consolidation threshold — recorded canonically in `policy-documentation` Rule 3). This policy is the first application: the frontmatter-quoting rule had crossed four surfaces before being consolidated here.
6. **Policy frontmatter carries a `domain:` field** (lint-checked, added 2026-05-24 by US-AGORA-008) — one of the canonical enum values: `discipline` · `authoring` · `ui` · `i18n` · `testing` · `migration` · `leveling`. Categorizes policies for structural discovery (which set of cross-cutting rules a new contributor needs to learn for a given domain) and for observability (`/wiki/stats` renders a `by_domain` distribution chart). Required on every `.claude/policies/policy-*.md` file; the lint surfaces missing or invalid values. `_TEMPLATE.md` carries the placeholder.
7. **Cite a rule by its title, a step by its heading** — a `policy-<slug> Rule <n>` citation carries the rule's title beside the number (`Rule 8 (*form inputs use the canonical macros*)`), a skill step is cited by its heading, a command by the name the click registry carries. The consistency lint's citation mode (US-AGORA-087) resolves each against its source: a number whose quoted title is another rule's is a re-pointed citation and reds the push; a bare number is warned and counted against a ratchet that only falls. Added 2026-11-02 after T-116's renumbering of `policy-frontend-conventions` left thirteen citing lines in five skills pointing at the wrong rules.

### policy-skill-progression -- Skill progression — leveling, metrics, promotion, regression <sup>([full text](.claude/policies/policy-skill-progression.md))</sup>

<!-- rc:policy-skill-progression -->
1. **Four levels — `draft / used / hardened / reference`.** Each level has a one-line capability claim, an **all-of metric gate**, and a **quest** (a deterministic file-checkable artifact that must exist for promotion). A skill is exactly one level at any time; the level lives in the SKILL.md frontmatter (`level:` + `promoted_at:` + at `used`+ `role:` + at `hardened`+ `epithet:`). New skills start at `draft`. Levels apply to **skills only**, never policies — policies have their separate `status:` enum (`draft / active / deprecated`).
2. **Five quantitative metrics + one qualitative trail.** Metrics are file-backed and deterministic — computed from `.claude/`, `docs/`, and Git history alone. **M1** invocation count (since last promotion-marker commit), **M2** correction load (`/learn` patches against SKILL.md since promotion), **M3** redo rate, **M4** reference depth (soft signal), **M5** cross-reference fan-in, **M6** last-update recency. **The qualitative trail is XP** — the per-skill experience log (Rule 6) carrying the *narrative* the metrics can't. Metrics gate; XP tells the story.
3. **Promotion is human-confirmed via `/level <skill> --promote`. No auto-promote, ever.** The system *surfaces* eligibility (computed "candidate-for-<next>" state at read time); the user confirms. The promotion-marker commit subject `level(skill): promote <name> <from> → <to>` is the immutable reference point for M1/M2's "since last promotion" computation. Every promotion + regression appends one entry to `IMPROVEMENTS.md`. Promotion `used → hardened` includes a **naming ceremony** (Rule 7) and requires a **`## Claims at this level` section** in the SKILL.md body (Rule 8).
4. **Regression is narrow — only on a `/learn` patch that contradicts a named claim the skill makes at its current level.** Threshold-based auto-regression is forbidden. High M2 surfaces as a `/level <skill>` audit finding ("3 patches since promotion — review for regression?") but never silently demotes. The contradicting-patch shape: `/learn` reads the `## Claims at this level` section of any `hardened`+ target and asks *per claim* whether the patch contradicts it. If any answer is yes, `/learn` calls `/level <skill> --regress --corrects <sha>`.
5. **`/level` is the only authorised writer.** Modes: `/level --board` (every skill ranked — the "character sheet" surface; without it the leveling system is invisible and dies), `/level <skill>` (audit one skill — "Holding tier" + "Reaching for next" two-column view), `/level <skill> --promote|--regress` (the level writes, including the naming ceremony), `/level <skill> --xp +<N> "<snippet>"` (append one XP entry — the granular writer, called by `/agora --end` and by hand). Direct edits to `level:` / `promoted_at:` / `epithet:` / experience.md bypass the audit trail and are a discipline violation.
6. **Each skill at `used`+ carries an append-only experience log at `.claude/skills/<name>/experience.md`** — markdown frontmatter (`xp_total`, `xp_by_level`, `last_xp_at`) + a `## Unrated journal` capture-at-source buffer + per-entry graded blocks (date · session · +XP · 🟢 success / 🟡 lesson · one-paragraph snippet). **Capture-at-source:** the invoked skill appends a one-line *unrated* stub to its own buffer when it finishes work in-session (a narrow carve-out from Rule 5 — unrated, so skill-writable). **Grade-at-end:** `/agora --end` step 2.3b reads the buffer, rates each stub as a 4-eye gate, and `/level <skill> --xp` converts + clears it. The `hardened → reference` gate adds `xp_total ≥ 200 across ≥ 15 sessions` (XP is the trajectory signal at the top tier; lower tiers gate on metrics alone). **The sidecar also holds `## Level history`** (US-AGORA-057, `AGORA-DECL §3`): every level transition `/level` writes and every `/learn` patch entry lands there, never in SKILL.md — whose own `## Level history`, where one still exists, is legacy and only shrinks, so the prose ratchet stays green on a lesson.
7. **Naming ceremony fires at `used → hardened`.** Three identity steps across the four levels: (i) at `draft → used`, the user sets a one-line `role:` frontmatter descriptor (*"the inspector"*, *"the doctor"*); (ii) at `used → hardened`, the **ceremony** — `/level` presents the skill with its capabilities + experience log + the Agora-philosophers catalog (Socrates / Aristotle / Euclid / Diogenes / Hero / Callimachus / Plato / Pythagoras / Heraclitus / Thales / Solon / Pericles / Anaxagoras / Theophrastus), the skill proposes ONE epithet + a one-sentence justification, user nods via 4-eye gate, `epithet:` is written; (iii) at `hardened → reference`, the epithet is canonicalized as a `## Identity` opening section that tells the story of why it fits.
8. **Hardened+ skills carry a `## Claims at this level` section in the SKILL.md body** — 3–5 explicit commitments the skill makes that other skills depend on. Each claim is one sentence naming an invariant. The section is a **quest requirement** for the `used → hardened` promotion (a skill that cannot enumerate 3 claims isn't yet hardened). At `hardened → reference`, the claims tighten — a `reference`-tier skill's claims read like rule statements that *other* skills cite. `/learn` reads the section per Rule 4: each named claim is the unit of the contradiction question.

### policy-skill-routing -- Skill routing — route work to skills, inline is the justified exception <sup>([full text](.claude/policies/policy-skill-routing.md))</sup>

<!-- rc:policy-skill-routing -->
1. **Route by default; inline is the named exception.** When non-trivial work matches an existing skill's purpose, invoke the skill — even if the user didn't name it. Doing it inline requires a **one-phrase justification** (no skill covers it · genuinely trivial · needs in-flight context a fresh invocation would lose). **Bugs route to `/fixbug` by default** — anything with a root cause worth diagnosing (misbehaviour, wrong style, silent data loss), even mid-session, even when the fix looks small, **and even when a sweep surfaced it** — a defect found inside a conversion or completeness sweep reads as part of the sweep and is not (lived twice, session 2026-09-01 · session 2026-09-02); a one-line typo or an in-flight tweak during a live verify round with the user present is the named exception (the 2026-07-29 ruling) — **a gate redirect that births or reshapes a STORY is not an in-flight tweak: it routes to `/new-story --from-plan` / `/update-story`** (lived session 2026-09-19: two stories authored inline at a ruling gate; `retro-context` warns on a `fix(`-typed seam with no `/fixbug` in the record — a sweep's own seam is `feat(`-typed, which is why the case is named here, not left to the check).
2. **The harness rule covers explicit invocation; this policy covers proactive routing.** When the user *types* `/skill` you must invoke it (the harness BLOCKING rule). This policy extends that to work the user *described but didn't name* — the gap where "felt faster inline" drift lives.
3. **Routing is how the agent wins the leveling game.** A skill earns M1 + XP only when it appears in `skills_invoked:` — it literally cannot level if unused. The agent's job in Agora is to level the skills; routing real work to them *is* the win condition (per `policy-skill-progression`).
4. **Planned at `--start`, caught at `--end`.** `/agora --start` step 1.4 routes planned work to skills; `/agora --end`'s **close-out paper** (2.10) surfaces every "did inline what a skill exists for" as a **missed-routing finding** that feeds the next session's plan.
5. **"Faster inline" is the smell, not the signal.** Inline feels faster because it skips the skill's scaffolding — but that scaffolding (surface-confirm gates, registry checks, wiki seeds, plan files) is what prevents the iteration rounds that cost *more* than it saved. Speed-to-goal counts the reworks.
<!-- /rc:policy-skill-routing -->

### policy-spawns -- Spawn discipline — when, how, and with what authorization <sup>([full text](.claude/policies/policy-spawns.md))</sup>

<!-- rc:policy-spawns -->
1. **Spawn when the sub-goal is separable, read-heavy, or context-budget-relieving — not as a default.** A spawn fits when (a) the sub-goal is research / drafting / web-search work, (b) walking it inline would derail the parent flow, or (c) the parent is approaching its context budget. Skills that need the parent's working tree, the parent's open changes, or the parent's full context do NOT spawn — they run inline.
2. **Authorization is per-spawn and stated in the briefing — three tiers.** `advisory` (return markdown in conversation — the default), `write` (Write/Edit allowlisted paths, NO commits), `commit` (commit allowlisted paths). Every briefing names its tier explicitly. Spawn output is **raw material** by default — the **parent's `/agora --end` commit-tree triage** stages and commits. Spawn-commits requires explicit `tier: commit` authorization in the briefing.
3. **Parallel reads OK; parallel writes never.** Multiple `advisory` spawns can run unrestricted. Multiple `write` spawns require **disjoint path allowlists** — the parent checks every open spawn's allowlist before dispatching the next one. Max **3 concurrent write-tier spawns** (the briefing-burden ceiling — past 3 the parent's bookkeeping costs more than the parallelism saves).
4. **The briefing is self-contained — five required sections.** **Background** (zero-context setup: what the parent system is, the relevant naming and abbreviations) · **Files to sweep** (concrete paths the spawn must read first) · **Constraints** (explicit "do NOT touch" path list — every file the parent is in flight on, by exact path) · **Deliverable shape** (testable: file path + structure + a size budget in the deliverable's own unit — tests, locators, rows, never lines — not "explore the area") · **Reply protocol** ("when you're done, reply with X, Y, Z — do NOT paste full file contents back"). Skipping any of the five is the most common cause of an iteration round.
5. **Delivery is auto by default; manual is the opt-in.** An **auto-spawn** is dispatched via the Agent tool — the subagent reads its own briefing file and writes its deliverable into the `## Result` block itself (no copy-paste). A **manual spawn** (copy-paste into an external window or a different model) is the opt-in alternative, used only when a *different model or separate context window* is the point. Auto delivery does NOT bypass the tier — a `write`/`commit` auto-spawn still goes through the parent's commit-tree triage.
6. **Lifecycle: clear, finite goal — then fade.** A spawn moves `open → returned → folded`. The parent folds the result into one Log entry and never touches it again (the `## Result` block is written by the subagent in auto mode, pasted by the user in manual mode). **Multi-iteration is normal** (~⅔ of real spawns iterate once or twice) — but documented **append-only** as `## Iteration 2`, `## Iteration 3` in the same spawn file. **Extra-scope discoveries come back as findings**, never as silent extension; the parent decides whether to dispatch a follow-up spawn, address inline, or park for a future session.
<!-- /rc:policy-spawns -->

### policy-commit-discipline -- Commit discipline — one concern per commit, properly documented, clean tree at session boundaries <sup>([full text](.claude/policies/policy-commit-discipline.md))</sup>

<!-- rc:policy-commit-discipline -->
1. **One commit, one concern.** Stage deliberately by path — never `git add -A` / `git add .`. Each commit is a single coherent change describable in one line.
2. **Conventional-commit messages.** `type(scope): summary` — `feat` / `fix` / `refactor` / `docs` / `test` / `chore` — imperative mood, ≤72-char subject. Reference the story id (`US-XXX-NNN`) when the change implements or advances one. **The `commit-msg` hook refuses a subject outside the form or over 72 characters** (US-AGORA-099); the detail belongs in the body.
3. **Co-author trailer is mandatory.** Every commit message ends with a `Co-Authored-By: Claude <model name> <noreply@anthropic.com>` trailer naming the model that actually authored the commit (per the harness's standing instruction — e.g. `Claude Fable 5`); never a stale hardcoded model.
4. **Commit only on explicit textual confirmation — declared at `--start`, executed at `--end`.** `/agora --start` (1.4c) proposes the session's **repo plan** (branch — a feature branch by default for non-trivial build work, **one branch per Milestone**; expected commit groupings; push disposition) on the session-plan gate the user is already reading. `--end`'s **close-out paper** (2.10) then proposes the actual commits as one section — **summarized**: grouped files + one-line subjects, no full bodies — compared against what was declared, and the user's **single nod** authorizes them. Full bodies are written only after that nod: presenting them in the proposal turns "go" into a rubber-stamp of text the user may not have read carefully. Smoke tests passing, ruff clean, manual verification — none of these are user confirmation; they are *prerequisites* to asking. **Auto-push fires only when the plan declared it, the close-gate is green, and the tree matches the declared groupings**; any divergence falls back to explicit confirm-then-push, and firing a Milestone tag is never automatic (2.2 keeps its own gate). The gate moved *earlier*, not away. Inside an open Milestone the branch is not composed at 1.4c but **read from the Goal's declaration and checked** — `flask agora milestone --goal "<Goal>"` (US-AGORA-039) reports batches / branch / CI and flags a session branch that diverges from the one the Milestone declares. **Named exception — the bot-PR amendment (AGORA-DECL §6, ruling 6; US-AGORA-110):** an unattended job commits to its own `bot/` branch and opens a PR; that PR is a proposal, the merge is the four-eye gate, and nothing merges or closes unattended.
5. **Milestones open and close clean, pushed, and green. Sessions may park between them.** `/agora --start` triages the previous session's leftovers; `/agora --end` triages this session's commits and always retros. When a session reaches a targeted Milestone, the ceremony fires — `flask stats dump` + annotated `git tag milestone-<slug>` + push + wait for CI green. When a session parks without a Milestone, it commits cleanly; push is optional; no CI gate. Uncommitted work never spans a session boundary.
<!-- /rc:policy-commit-discipline -->

### policy-issue-templates -- GitHub Issue templates — agora:type:* axis labels at create-time <sup>([full text](.claude/policies/policy-issue-templates.md))</sup>

<!-- rc:policy-issue-templates -->
1. **Every new external-facing Issue surface at GitHub uses one of the 6 markdown templates** at `.github/ISSUE_TEMPLATE/` — `agora-bug.md`, `agora-goal.md`, `agora-sub-goal.md`, `agora-section.md`, `agora-milestone.md`, `agora-learn.md`. Each auto-applies its `agora:type:*` label, so no triage step is needed at `/agora --start`.
2. **Markdown templates, not YAML form fields.** The user's workflow is "write a prompt in an Issue and we work on making it structured" — markdown gives an editable starting point with sections to fill in; YAML form fields enforce validation that gets in the way of freeform prompting. The six templates in `.github/ISSUE_TEMPLATE/` are the canonical shape.
3. **`config.yml` keeps `blank_issues_enabled: true`** so users are never locked out of opening a plain Issue. The template chooser is a guide, not a fence. `contact_links:` in the chooser point at the Agora vocabulary README and the product's story backlog — the two references a confused user would want first.
4. **Adding a new template means adding a new `agora:type:*` axis value** — the template-to-axis mapping is one-to-one by design. Extend `_CANONICAL_LABELS` in `app/commands/agora_helper.py` AND run `flask agora setup-labels` before merging the new template, otherwise GitHub rejects the unknown label at Issue creation.
5. **The bug template is the live-traffic one.** `/agora --start` step 1.1 queries `flask agora list-bugs` (filtered by `agora:type:bug --state open`) as a candidate-intents source. The other five templates (goal / sub-goal / section / milestone / learn) are for occasional cross-referencing — `agora:type:goal` Issues mirror COMPASS Goals one-way; `agora:type:milestone` Issues track a (possibly multi-Goal) effort with its game-plan living in the Issue (US-AGORA-019/021); `agora:type:learn` Issues are optional external echoes of skill-level lessons; `agora:type:section` Issues are optional retro mirrors.
6. **Goal/Sub-goal hierarchy + Milestone-tag timing.** Every sub-goal Issue references a parent Goal Issue (`**Parent Goal:** #<n>`) — a Milestone's **batch** Issues are scaffolded from that shape in one call via `flask agora batches --goal <n> --batch "…"`, never hand-written as scope accretes. Every Goal Issue is **Backlog** (GH-only, no Milestone tag) or **Active** (mirrored in COMPASS with committed success criteria AND a declared `milestone-<slug>` tag) — Backlog → Active moves in the same `/agora --start` step 1.4 edit when a session picks the Goal up. The Milestone tag is the *closing contract*; declared at COMPASS entry, fired at Goal closure, immutable once declared. The GH `milestone:` attribute is **orthogonal** — it's a **tier / release group** (Tier 3, Release 2), not an Agora Milestone; tiers can be reassigned freely. User-friendly framing: *"a tier is where it sits in the queue; a Milestone is what we'll call it when it ships."*
7. **Issues close when their work ships — at `/agora --end` step 2.8b.** A Goal mirror Issue closes when its Milestone fires (Path A step 7); a sub-goal / section Issue closes when the session that finished its deliverable closes (step 2.8b, both paths). Closing is a **4-eye gate** — propose the close list, the user nods, since closing is an outward GitHub-state action that never auto-fires. Every close carries a **citing comment** linking the Issue back to the closing session + commits/tag. Done work that stays open makes the board lie (the gap that motivated this rule: #74 + #75 shipped 2026-05-20 yet sat open until 2026-05-21).

### policy-documentation -- Documentation <sup>([full text](.claude/policies/policy-documentation.md))</sup>

1. Every **implemented** feature has a wiki seed at `docs/wiki/feature-<slug>.md` (path config) — narrative source of truth, authored by `/implement-story` Phase 3.8.
2. Every **non-trivial** feature has an implementation plan at `docs/implementation-plans/implementation-plan-<id-or-slug>.md` — written **before** code (Phase 2b) and updated **during** implementation with a Surprises & decisions entry per phase.
3. **Cross-cutting** rules that span two or more skills go in `.claude/policies/policy-<slug>.md` (authored via `/document --policy`) — never duplicated across skill SKILL.md prompts. **A scattered rule earns its own policy once the same rule lives in ≥3 places** (the consolidation threshold).
4. **Skill-level corrections** (a skill misbehaved or missed a step) go through `/learn` — they patch the relevant SKILL.md surgically and never become a policy or wiki seed.
5. Story status flips reflect work state: `draft → review → approved → planned → in-progress → partially-implemented → implemented → tested`. The implementation plan's `Status:` field tracks the build separately (`draft → in-progress → done`).
